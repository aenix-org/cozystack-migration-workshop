# Лаба 12 · Виртуалка рядом с контейнерами

| | |
|---|---|
| **Время** | 30 минут, из них 5–10 — ожидание загрузки машины |
| **Что доказывает** | Легаси не нужно контейнеризовать, чтобы переехать. Виртуалки и контейнеры живут в одном кластере |
| **Что понадобится** | Кластер из лабы 0, приложение из лабы 1, `kubectl`, `~/lab.kubeconfig`, доступ в дашборд тенанта |

## Зачем это

Справочник сотрудников — самая старая часть «Пропуска». Приложение 2011 года, написано
подрядчиком, которого больше нет. Работает на Windows Server и на версии .NET, которую
не обновляли, потому что «оно работает». Исходников нет, документации нет, есть
инструкция по восстановлению на четыре страницы, и в ней шаг «позвонить Сергею».

Переезжать в контейнер этот справочник не будет. Не «пока», а никогда: контейнеризовать
приложение, которое некому пересобрать, невозможно физически.

И это не повод отказываться от переезда. В этой лабе мы поднимем виртуальную машину
**рядом** с контейнерами — в том же кластере, в том же интерфейсе, по тому же API — и
свяжем её с контейнерным приложением.

Это, пожалуй, главная лаба всего воркшопа. Не потому что она сложная — она как раз
простая. А потому что она отвечает на вопрос, который стоит за всей миграцией: «а что
делать с тем, что не переносится?»

Ответ: ничего. Оставить как есть и перевезти как есть.

## Словарик

| Термин | Что это | Аналог в vSphere | Где аналогия врёт |
|---|---|---|---|
| VMInstance | Виртуальная машина как объект кластера | Виртуальная машина | Описывается текстом и создаётся тем же `kubectl`, что и приложения |
| VMDisk | Диск, существующий отдельно от машины | vmdk | Отдельный объект: переживает машину, подключается к другой |
| Instance type | Готовый размер машины из справочника | — | Ближе к типам инстансов в облаках, чем к ручной настройке vCPU/RAM |
| Instance profile | Набор устройств и драйверов под гостевую ОС | Guest OS type | Влияет на то, какие контроллеры увидит гость |
| cloud-init | Скрипт первичной настройки при первом включении | Customization Specification | Обычный YAML внутри манифеста, а не мастер в интерфейсе |
| Service типа LoadBalancer | Постоянный адрес приложения, видимый снаружи кластера | VIP на балансировщике | Адрес выделяет платформа, заявку никуда подавать не нужно |
| ClusterIP | Адрес приложения, видимый только внутри кластера | Внутренний VIP | Снаружи кластера этот адрес не существует. Совсем |
| KubeVirt | Механизм, которым Kubernetes запускает виртуалки | Гипервизор | Это не второй гипервизор: под капотом тот же QEMU/KVM, что и у любого Linux |

## Шаг 1. Поднимаем виртуалку

📍 **Где:** в браузере, в дашборде тенанта.

Виртуалка — это managed-сервис Cozystack, она живёт **не внутри кластера `lab`**, а
в вашем тенанте, рядом с ним. Ровно там же, где живёт сам кластер `lab`: если помните
лабу 0, узел кластера — это тоже виртуальная машина в вашем тенанте.

Заводится она в два приёма, и это стоит понять сразу.

### Сначала диск

Тенант → **Создать приложение** → `VM Disk`.

| Поле | Значение | Почему так |
|---|---|---|
| Имя | `spravochnik` | так будет называться и машина |
| Source | `Image` → `ubuntu-22.04` | берём из готовой коллекции образов платформы |
| Storage | `10Gi` | справочнику хватит с запасом |
| Storage class | `replicated` | три копии данных на разных узлах |

**Почему диск — отдельный объект, а не поле внутри машины.** Потому что диск переживает
машину. Машину можно удалить целиком, пересоздать с другим типом, другой сетью, другим
именем — и подключить тот же диск. В vSphere вы делаете то же самое, отцепляя vmdk от
одной VM и цепляя к другой; здесь это выражено в модели явно.

Дождитесь, пока диск наполнится: платформа скачивает и разворачивает образ, это минута-две.

### Потом машина

Тенант → **Создать приложение** → `VM Instance`.

| Поле | Значение | Почему так |
|---|---|---|
| Имя | `spravochnik` | |
| Instance type | `u1.medium` | 1 процессор, 4 ГБ — тот же справочник размеров, что у узлов кластера |
| Instance profile | `ubuntu` | набор устройств под гостевую ОС |
| Run strategy | `Always` | держать включённой; выключится сама — включат снова |
| Disks | `spravochnik` | тот диск, который вы создали |
| Cloud init | см. ниже | нужен пароль, чтобы войти в консоль |

В поле cloud-init:

```yaml
#cloud-config
password: ubuntu
chpasswd: { expire: false }
ssh_pwauth: true
packages: [ curl ]
```

⚠️ **Пароль в открытом виде — только для лабы.** На рабочей машине здесь были бы
`sshKeys`, а пароля не было бы вовсе. Мы идём коротким путём, чтобы не тратить время
воркшопа на обмен ключами.

**То же самое текстом**, если вам ближе так:

```bash
export KUBECONFIG=~/.kube/workshop   # тенантный доступ, не lab.kubeconfig
kubectl apply -f staff-directory-vm.yaml   # tenant-workshopXX заменить на свой
```

<details>
<summary><b>Разбираем staff-directory-vm.yaml построчно</b></summary>

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: VMDisk
```

Та же группа API, в которой живут бакеты, базы и очереди. Виртуальная машина здесь —
не отдельная подсистема со своим интерфейсом, а такой же объект каталога, как Redis.
Это и есть содержательная часть фразы «в одном интерфейсе и по одному API».

```yaml
spec:
  source:
    image:
      name: ubuntu-22.04
```

Имя из общей коллекции образов платформы, а не URL. Коллекция общая на весь кластер:
образ скачивается один раз, а не каждым тенантом заново. Если нужен свой образ — там же
есть `source.http` с ссылкой и `source.disk` для клонирования существующего диска.

```yaml
kind: VMInstance
spec:
  instanceType: u1.medium
```

Размер машины берётся из справочника, а не набирается руками. `u1.medium` — это 1
процессор и 4 ГБ. Тот же самый справочник вы видели в лабе 0, когда заказывали узел
кластера, и это не совпадение: узел кластера — такая же VMInstance.

```yaml
  instanceProfile: ubuntu
```

Профиль гостевой ОС: какие контроллеры, драйверы и устройства подсунуть машине, чтобы
гость их узнал. Ближайший аналог — «Guest OS type» при создании VM в vSphere, и последствия
такие же: неправильный профиль даёт машину, которая грузится, но не видит диск.

```yaml
  runStrategy: Always
```

Желаемое состояние питания. `Always` — держать включённой: если гость выключится изнутри,
машину включат снова. `Halted` — выключена. `Manual` — как оставили, никто не вмешивается.

Обратите внимание на формулировку, она та же, что у `replicas` в Deployment: не «включи»,
а «держи включённой».

```yaml
  disks:
    - name: spravochnik
```

Список дисков по именам объектов VMDisk. Второй диск под данные добавляется сюда же
второй строкой.

```yaml
  cloudInit: |
    #cloud-config
    password: ubuntu
```

cloud-init — стандартный механизм первичной настройки, который понимают все облачные
образы Linux. Отрабатывает один раз, при первом включении. Аналог Customization
Specification в vSphere, только это текст внутри манифеста, а не мастер в интерфейсе, —
значит, лежит в Git и ревьюится вместе с остальным.

### Чего в этом манифесте нет и не будет

**Поля `replicas`.** Его в `VMInstance` нет. Виртуальная машина — это один объект;
нужны две машины — заводите два объекта с разными именами.

Это принципиальное отличие от `Deployment`, и оно не недоработка. Копии в Deployment
взаимозаменяемы: любая обслужит любой запрос, и потерять одну не страшно. Виртуальные
машины не взаимозаменяемы — у каждой своё состояние на своём диске, и «создать ещё одну
такую же» означает совсем не то, что для контейнера.

Практическое следствие: **самолечения, которое вы видели в лабе про удаление пода, у
виртуалки нет.** Удалите под — кластер создаст новый за секунды. Удалите VMInstance —
машина исчезнет, и вернуть её можно только руками, подцепив уцелевший диск. Здесь вы
ровно там же, где были в vSphere, и это надо знать заранее, а не выяснять в процессе.

</details>

Дождитесь, пока машина поднимется. Первое включение идёт 3–5 минут: cloud-init
разворачивает файловую систему на весь диск и ставит пакеты.

## Шаг 2. Заходим в машину

📍 **Где:** в дашборде, в карточке машины `spravochnik`.

В карточке есть консоль — это тот же экран, что и «Open Console» в vSphere. Откройте её.

Логин `ubuntu`, пароль `ubuntu`.

⚠️ **Если консоль показывает чёрный экран и мигающий курсор — подождите.** cloud-init
ещё не закончил, приглашение появится само. Не перезагружайте машину: перезагрузка
посреди cloud-init оставит её в наполовину настроенном состоянии.

**Тот же вход из терминала**, если поставили `virtctl` (см. `workshop/README.md`):

```bash
export KUBECONFIG=~/.kube/workshop
kubectl virt console spravochnik -n tenant-workshopXX
```

Выход из консоли `virtctl` — `Ctrl+]`.

Осмотритесь. Это обычная Ubuntu:

```bash
uname -a
ip a
free -m
```

Никаких следов Kubernetes внутри нет и не должно быть. Гость не знает, что он в
кластере, и ему это не нужно — ровно как виртуалке в vSphere не нужно знать про vCenter.

## Шаг 3. Пробуем достучаться до приложения — и не выходит

Теперь свяжем машину с контейнерным приложением.

Целиться будем в `rickroll` — то самое учебное приложение из первой лабы. Не в настоящий
`passes-api`, и вот почему: нас здесь интересует ровно одно — **дойдёт ли сетевой пакет из
виртуальной машины до контейнера**. Для этой проверки чем проще мишень, тем лучше: если
что-то не сработает, вы будете разбираться с сетью, а не гадать, не в приложении ли дело.

Как только связь подтвердится, тот же самый адрес подставляется в настоящий сервис без
единого изменения — для сети между ними нет никакой разницы.

📍 **Где:** на ноутбуке, в отдельном окне терминала.

Узнайте адрес приложения:

```bash
export KUBECONFIG=~/lab.kubeconfig
kubectl get svc rickroll
```

```
NAME       TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
rickroll   ClusterIP   10.96.140.211   <none>        80/TCP     2h
```

📍 **Где:** в консоли виртуальной машины.

```bash
curl --max-time 5 http://10.96.140.211
```

**Что вы увидите:**

```
curl: (28) Connection timed out after 5001 milliseconds
```

> **Остановитесь и подумайте, прежде чем читать дальше.**
>
> Машина и кластер — в одном тенанте, на одном железе, у одной платформы. Почему пакет
> не доходит?

<details>
<summary><b>Ответ и урок шире, чем эта ошибка</b></summary>

Потому что адреса `10.96.140.211` **не существует нигде, кроме кластера `lab`**.

`ClusterIP` — это не адрес в сети. Это запись в правилах, которые кластер расставляет
на своих узлах: «пакет на 10.96.140.211:80 отправить в один из подов с меткой
`app: rickroll`». Правила стоят на узлах кластера `lab` и больше нигде. Виртуальная
машина в них не участвует — она не узел этого кластера, — поэтому для неё этот адрес
указывает в пустоту.

Колонка `TYPE` в выводе `kubectl get svc` — как раз про это: она отвечает на вопрос
«кому этот адрес виден».

| Тип Service | Кому виден | Когда нужен |
|---|---|---|
| `ClusterIP` | только подам внутри этого кластера | связь между частями одного приложения |
| `NodePort` | всем, кто дотянется до узлов, по большому номеру порта | отладка, редко что-то ещё |
| `LoadBalancer` | всем, кто дотянется до выданного адреса | вход снаружи кластера |

**Урок шире, чем эта ошибка.** «Внутри кластера» — это не метафора и не про сетевую
безопасность. Это буквально разные адресные пространства. Причём границу проводит не
файрвол, который можно попросить открыть, а само устройство сети: снаружи такого
адреса нет, открывать нечего.

Тот же вывод объясняет, почему в первой лабе браузер попадал на приложение только через
`port-forward`: ваш ноутбук — тоже «снаружи».

</details>

## Шаг 4. Выдаём приложению адрес, видимый снаружи

📍 **Где:** на ноутбуке.

В папке лежит `rickroll-lb.yaml`. Разберём и применим.

<details>
<summary><b>Разбираем rickroll-lb.yaml построчно</b></summary>

```yaml
kind: Service
metadata:
  name: rickroll-lb
spec:
  type: LoadBalancer
  selector:
    app: rickroll
  ports:
    - port: 80
      targetPort: http
```

Всего одно отличие от Service из первой лабы — строка `type: LoadBalancer`. Всё
остальное то же самое: тот же отбор подов по метке `app: rickroll`, тот же порт.

**Почему отдельным объектом, а не правкой существующего Service.** Внешний адрес нужен
ровно на одну лабу. Отдельный объект удаляется одной командой и не трогает то, что
работало до него. То же соображение работает и в жизни: временный доступ лучше делать
отдельной сущностью, которую не жалко и не страшно удалить.

**Откуда берётся адрес.** Ваш кластер `lab` — это кластер внутри тенанта, и у него есть
свой драйвер платформы (в терминах Kubernetes — cloud provider). Когда вы создаёте
Service типа `LoadBalancer`, происходит вот что:

1. Кластер `lab` видит Service, для которого нужен внешний адрес, и обращается к
   платформе.
2. Платформа создаёт **в вашем тенанте**, рядом с виртуалками, свой объект-адрес и
   привязывает его к узлам кластера `lab`.
3. Полученный адрес возвращается обратно в кластер `lab` и появляется в колонке
   `EXTERNAL-IP`.

Отсюда два следствия, которые стоит удержать в голове.

Первое: адрес выделяется **автоматически и за секунды**. Заявку никуда подавать не надо,
согласовывать не надо, свободный адрес искать в таблице не надо.

Второе: адрес принадлежит **сети тенанта**. Виртуалки вашего тенанта его видят —
именно поэтому лаба работает. Из интернета он не виден, и это правильное поведение по
умолчанию: наружу приложение выставляют осознанно, а не по факту создания Service.

⚠️ Слово «внешний» в `EXTERNAL-IP` означает «внешний по отношению к кластеру `lab`»,
а не «доступный из интернета». Путаница на этом месте — очень частая.

</details>

Применяем:

```bash
export KUBECONFIG=~/lab.kubeconfig
kubectl apply -f rickroll-lb.yaml
```

Адрес выделяется не мгновенно — несколько секунд:

```bash
kubectl get svc rickroll-lb -w
```

**Что вы должны увидеть** — сначала `<pending>`, потом настоящий адрес:

```
NAME          TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)        AGE
rickroll-lb   LoadBalancer   10.96.201.77    <pending>       80:31544/TCP   3s
rickroll-lb   LoadBalancer   10.96.201.77    10.244.13.42    80:31544/TCP   12s
```

Прервите слежение `Ctrl+C`. Запишите адрес из колонки `EXTERNAL-IP`.

⚠️ **Если `<pending>` не сменяется адресом дольше минуты** — значит, драйвер платформы
не смог выделить адрес. Смотрите события:
`kubectl describe svc rickroll-lb | sed -n '/Events:/,$p'`.

## Шаг 5. Виртуалка разговаривает с контейнером

📍 **Где:** в консоли виртуальной машины.

```bash
curl http://10.244.13.42
```

Подставьте свой адрес из `EXTERNAL-IP`.

**Что вы должны увидеть** — HTML страницы из первой лабы, а в нём строку с именем пода:

```html
<div class="pod">вас обслужил под<b>rickroll-7d9f8c6b4-xk2mp</b></div>
```

Проверьте, что это правда тот под:

```bash
export KUBECONFIG=~/lab.kubeconfig
kubectl get pods -l app=rickroll
```

Имена совпадают.

**Остановитесь на секунду и посмотрите, что сейчас произошло.**

Виртуальная машина с Ubuntu, которая ничего не знает про Kubernetes, обратилась по
обычному TCP на обычный адрес и получила ответ от процесса, живущего в контейнере на
узле соседнего кластера. Без агентов внутри гостя. Без шлюзов. Без «интеграции».

Именно это и означает «легаси не надо контейнеризовать». Справочник 2011 года на Windows
Server продолжит работать так, как работал, — а новые части «Пропуска» будут ходить к нему
и он к ним, потому что между ними обычная сеть.

Если у вас осталось время — сделайте обратную проверку. Поднимите на машине что-нибудь,
слушающее порт:

```bash
python3 -m http.server 8000
```

И сходите туда из кластера `lab`:

```bash
kubectl run probe --rm -it --restart=Never --image=curlimages/curl:8.11.1 \
  -- curl -s --max-time 5 http://<адрес-виртуалки>:8000
```

Адрес виртуалки виден в дашборде в её карточке или командой
`kubectl get vminstance spravochnik -n tenant-workshopXX -o wide`.

Связь работает в обе стороны, и ни одна сторона не знает, кто на другом конце.

## Проверка

📍 **Где:** на ноутбуке, в том же окне терминала, где вы работали с `kubectl`.

```bash
export KUBECONFIG=~/lab.kubeconfig
export COZY_TENANT=workshopXX               # ваш логин без слова tenant-
export COZY_KUBECONFIG=~/.kube/workshop     # тенантный доступ
./check.sh
```

⚠️ **На Windows скрипт запускается из WSL**, а не из PowerShell — как его поставить,
написано в начале лабы 0. Без WSL лабу можно пройти, но отчёта-артефакта не будет.

Скрипт проверяет не наличие объектов, а связность: внешний адрес выдан, приложение по
нему отвечает и отдаёт имя настоящего пода, машина запущена и находится в той же сети
тенанта, что и выданный адрес.

`COZY_TENANT` обязателен — без него скрипт остановится сразу. `COZY_KUBECONFIG` можно не
задавать, если тенантный доступ лежит в `~/.kube/workshop`; если файла нет, проверки со
стороны тенанта будут пропущены с предупреждением, а часть про кластер отработает.

## Уборка

Внешний адрес нужен был на одну лабу — освободите его:

```bash
export KUBECONFIG=~/lab.kubeconfig
kubectl delete -f rickroll-lb.yaml
```

Виртуальную машину оставьте, если планируете лабу про мониторинг: её потребление тоже
видно в графиках, и это хорошая иллюстрация. Если не планируете — удалите машину и диск
через дашборд.

⚠️ **Удаляйте в правильном порядке: сначала машину, потом диск.** Диск, подключённый
к работающей машине, не удалится, и вы получите объект, висящий в состоянии удаления.

Стоимость уборки здесь честно выше, чем в остальных лабах: диск с данными — это диск с
данными, и мгновенно он не исчезает. Зато и создание было в один приём.

## А в vSphere это было бы

Виртуалка в vSphere — это домашняя территория, и делается она там привычно. Разница не
в самой машине, а в том, что рядом.

Чтобы связать эту машину с контейнерным приложением в vSphere, вам понадобился бы
Kubernetes — отдельным продуктом, отдельной лицензией, отдельным проектом внедрения.
Потом сеть между ним и виртуалками. Потом балансировщик, чтобы у приложения появился
адрес, и заявка на этот адрес. Три команды, три системы, три места, где что-то может
быть настроено не так, и один общий вопрос «а кто это всё эксплуатирует».

Здесь машина и приложение — объекты одного каталога, в одном интерфейсе, с одним
механизмом прав.

**Где vSphere удобнее, честно.** По части управления самими виртуальными машинами
vCenter пока богаче, и делать вид, что это не так, глупо:

| Что | vSphere | Cozystack |
|---|---|---|
| Шаблоны и клонирование | зрелые, с кастомизацией гостя | есть клонирование диска, мастера кастомизации нет |
| Снапшоты | привычные, с деревом | есть, но экосистема вокруг них моложе |
| Живая миграция | vMotion, отлаженный годами | есть, но применяется реже и проверена меньше |
| Права на папку с VM | гранулярные | права на уровне тенанта, папок нет |
| Консоль и инструменты гостя | VMware Tools со всей телеметрией | qemu-guest-agent, данных меньше |

Если вам нужны **только** виртуальные машины — честный ответ состоит в том, что переезд
ради переезда смысла не имеет. Выигрыш появляется там, где рядом с виртуалками нужно
что-то ещё: кластеры, базы, очереди, реестры, объектное хранилище. Тогда вместо пяти
продуктов с пятью моделями прав у вас один каталог, и справочник 2011 года стоит в нём
рядом с остальным.
