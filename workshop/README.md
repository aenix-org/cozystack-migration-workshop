# Воркшоп: миграция VMware-VM в Cozystack

Берём приложение, которое годами работало на виртуальной машине в VMware, и
перевозим его в Cozystack. Всё делаете своими руками. В репозитории лежат готовые
файлы описаний, скрипты и шпаргалка с командами.

## Что предстоит сделать

Приложение живёт на трёх машинах: само приложение, база данных и очередь сообщений.
Перевозим только первую — база и очередь останутся в прошлом, вместо них возьмём
готовые из каталога Cozystack.

Дорога состоит из четырёх участков.

**Вывозим диск.** Диск виртуальной машины из VMware записан в формате, который на
новом месте не читается. Его нужно переупаковать. Для этого поднимем временную
машину с нужными инструментами, сделаем дело внутри неё и погасим — ставить их себе
на ноутбук ради одного раза незачем.

**Кладём образ в хранилище.** Переупакованный диск нужно положить туда, откуда его
заберёт платформа. Заведём для этого своё хранилище — по смыслу это папка, доступная
по сети, только с собственным адресом и ключами.

**Поднимаем машину на новом месте.** Из вывезенного образа создаём виртуальную
машину уже в Cozystack. Сети внутри у неё сначала не будет: железо вокруг стало
другим, и настройки старой сетевой карты больше ни к чему не подходят. Починим
руками — заодно увидите, как это выглядит и сколько занимает.

**Подключаем базу и очередь.** Заказываем в каталоге готовые PostgreSQL и Kafka,
после чего правим настройки приложения: там прописаны адреса старых машин, их надо
заменить на новые. После этого заказы, которые создаёт приложение, снова пишутся в
базу и уходят в очередь — только теперь за этими двумя сервисами следит платформа,
а не вы.

## Доступы

Их выдаёт ведущий:

* дашборд https://dashboard.workshop.aenix.io
* логин `workshopXX`, пароль скажут на месте
* kubeconfig берётся в дашборде: Info, вкладка Secrets, секрет `kubeconfig-tenant-workshopXX`

Дальше везде `tenant-workshopXX` меняйте на свой namespace.

## Инструменты

Нужны `kubectl`, `virtctl` и `kubelogin`. Все три есть под Linux, macOS и Windows.

`kubectl` ставится по официальной инструкции https://kubernetes.io/docs/tasks/tools/
(на Linux это curl бинарника, на macOS `brew install kubectl`, на Windows
`winget install -e --id Kubernetes.kubectl`).

`virtctl` и `kubelogin` ставятся отдельными файлами — команды под каждую систему ниже.

⚠️ **Не ставьте krew ради этого воркшопа.** Это менеджер дополнений для `kubectl`, и
через него те же две утилиты тоже ставятся — но на прошлых воркшопах именно он съел
больше всего времени. На Windows он обычно вообще не работает: падает с `A required
privilege is not held by the client`, потому что создаёт символьные ссылки, а это
требует «Режима разработчика» или прав администратора, и на корпоративных ноутбуках
закрыто. На macOS и Linux он работает, но добавляет ещё один шаг, который может
сломаться, — а выигрыша не даёт: файлов всё равно два.

Если krew у вас уже стоит и вы им пользуетесь — `kubectl krew install virt` и
`kubectl krew install oidc-login` сделают то же самое. Если не стоит — не начинайте
сегодня.

**Windows** (PowerShell, папка `$HOME\bin` и её добавление в PATH — см. установку kubectl):

```powershell
# virtctl
$ver = (Invoke-RestMethod https://api.github.com/repos/kubevirt/kubevirt/releases/latest).tag_name
New-Item -ItemType Directory -Force "$HOME\bin" | Out-Null
Invoke-WebRequest -Uri "https://github.com/kubevirt/kubevirt/releases/download/$ver/virtctl-$ver-windows-amd64.exe" -OutFile "$HOME\bin\virtctl.exe"
# kubelogin -> имя плагина обязательно kubectl-oidc_login.exe
Invoke-WebRequest -Uri "https://github.com/int128/kubelogin/releases/latest/download/kubelogin_windows_amd64.zip" -OutFile "$HOME\kubelogin.zip"
Expand-Archive -Force "$HOME\kubelogin.zip" "$HOME\kl"
Move-Item -Force "$HOME\kl\kubelogin.exe" "$HOME\bin\kubectl-oidc_login.exe"
Remove-Item -Recurse -Force "$HOME\kubelogin.zip","$HOME\kl"
```

Откройте новое окно PowerShell и проверьте: `virtctl version`, `kubectl oidc-login --help`.
На macOS/Linux те же бинарники лежат на релизах KubeVirt
(https://github.com/kubevirt/kubevirt/releases) и kubelogin
(https://github.com/int128/kubelogin/releases, на macOS ещё
`brew install int128/kubelogin/kubelogin`).

kubelogin нужен, потому что kubeconfig ходит в кластер через Keycloak: при первом
`kubectl` откроется браузер, залогиньтесь как `workshopXX`.

Место, где легко споткнуться: `KUBECONFIG` должен указывать ровно на тот файл,
куда вы вставили kubeconfig. macOS/Linux:

```bash
export KUBECONFIG=~/.kube/workshop
kubectl config current-context
kubectl get vminstance -n tenant-workshopXX
```

Windows (PowerShell) — переменную задаём и на текущее окно, и на будущие:

```powershell
New-Item -ItemType Directory -Force "$HOME\.kube" | Out-Null
notepad "$HOME\.kube\workshop"    # вставьте kubeconfig; тип файла = Все файлы, иначе Блокнот добавит .txt
[Environment]::SetEnvironmentVariable("KUBECONFIG", "$HOME\.kube\workshop", "User")
$env:KUBECONFIG = "$HOME\.kube\workshop"
kubectl get vminstance -n tenant-workshopXX
```

Если kubectl отвечает `dial tcp [::1]:8080 ... refused` (или `localhost:8080`) — он не
видит kubeconfig: переменная `KUBECONFIG` не задана в этом окне или указывает не на тот
файл. На Windows `$env:KUBECONFIG` живёт только в текущем окне, поэтому его и закрепляют
через `SetEnvironmentVariable(... "User")`.

Кстати, `kubectl get vmi` или `vm` под тенантом не сработают, `kubevirt.io`
напрямую закрыт. Смотрите `vminstance`.

## Что где лежит и как применять

Склонируйте репу:

```bash
git clone git@github.com:aenix-org/cozystack-migration-workshop.git
cd cozystack-migration-workshop/workshop
```

Дальше важный момент. Во всех файлах вместо вашего namespace стоит заглушка
`tenant-workshopXX`. Если применить манифест как есть, он уедет не туда или вернёт
ошибку. Поэтому первым делом подставьте свой номер во все файлы разом. Допустим,
ваш логин `workshop03`, тогда:

```bash
# Linux
find manifests scripts -type f -exec sed -i 's/tenant-workshopXX/tenant-workshop03/g' {} +
# macOS (там sed чуть другой)
find manifests scripts -type f -exec sed -i '' 's/tenant-workshopXX/tenant-workshop03/g' {} +
```

Проверьте, что подставилось (не должно остаться ни одного `tenant-workshopXX`):

```bash
grep -rn tenant-workshopXX manifests scripts || echo "чисто, можно продолжать"
```

Одну вещь эта команда не тронет: в `manifests/03-app-vm.yaml` есть строка
`url: "ВСТАВЬТЕ_PRESIGNED_URL"`. Эту ссылку вы получите позже, когда сконвертируете
образ (её напечатает `convert.sh`), и впишете руками перед третьей фазой. Пока
имейте в виду, что она там ждёт.

Теперь про два типа файлов, они работают по-разному.

Манифесты из `manifests/` вы применяете со своей машины через `kubectl apply`. Это
описания того, что создать в кластере (бакет, виртуалки, базы).

Скрипты из `scripts/` вы запускаете не у себя, а внутри виртуалки. Порядок такой:
открываете скрипт в редакторе, вписываете свои значения вместо `ВСТАВЬТЕ_...`
(их берёте в дашборде), заходите в нужную VM через `virtctl console`,
переносите туда текст скрипта (проще всего открыть `nano имя.sh`, вставить,
сохранить) и запускаете `bash имя.sh`.

Разборы файлов убраны под спойлеры — если хотите просто идти по шагам, не раскрывайте.

### Фаза 1. Заводим хранилище под образ

📍 **Где:** на ноутбуке.

```bash
kubectl apply -f manifests/01-bucket.yaml
```

**Зачем.** Переупакованный диск надо куда-то положить, чтобы платформа потом забрала его
по ссылке. Обычная папка не подойдёт: файл должен быть доступен по сети и по протоколу,
который понимает Cozystack. Заводим объектное хранилище — по смыслу сетевая папка со
своим адресом, логином и паролем.

<details>
<summary><b>Что внутри 01-bucket.yaml</b></summary>

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: Bucket
metadata:
  name: my-images
  namespace: tenant-workshopXX
spec:
  users:
    app: {}
```

`kind: Bucket` — тип объекта из каталога Cozystack. Файл не описывает, *как* поднять
хранилище: он говорит платформе «хочу хранилище», а всё остальное она делает сама.

`namespace: tenant-workshopXX` — ваш участок платформы. Это единственное место, которое
нужно поменять руками: подставьте свой номер вместо `XX`.

`users: app: {}` — заводит пользователя с именем `app`. Пустые фигурные скобки означают
«настройки по умолчанию»: платформа сама придумает ему ключи доступа и положит их в
отдельный объект, который вы потом откроете в дашборде.

Обратите внимание, чего в файле **нет**: размера диска, адреса, портов, сертификата.
Всё это платформа определяет сама.

</details>

**Что дальше.** Ключи доступа берёте в дашборде: `Bucket` → ваш бакет → вкладка
`Secrets`. Понадобятся три значения — `bucketName`, `accessKey`, `secretKey`. Впишете их
в скрипт на следующей фазе.

### Фаза 2. Переупаковываем диск

📍 **Где:** сначала на ноутбуке, потом внутри временной машины.

```bash
kubectl apply -f manifests/02-conversion-vm.yaml
```

**Зачем.** Диск виртуальной машины из VMware записан в формате `VMDK` и упакован в файл
`OVA`. На новом месте работает другой гипервизор, ему нужен формат `QCOW2`. Содержимое
то же самое — ваша система со всем добром, — а упаковка разная.

Инструмент для переупаковки называется `virt-v2v`. Он работает только под Linux, тянет за
собой пару десятков зависимостей и жуёт десятки гигабайт. Ставить это на рабочий ноутбук
ради одного раза незачем, а на Windows и macOS он просто не поедет. Поэтому поднимаем
временную машину рядом с хранилищем, делаем дело внутри и гасим.

Так же поступают и в реальных проектах миграции: конвертер живёт рядом с данными, а не на
чьём-то ноутбуке через VPN.

<details>
<summary><b>Что внутри 02-conversion-vm.yaml</b></summary>

В файле **два** объекта, разделённых строкой `---`. Виртуальной машины без диска не
бывает, поэтому диск описывается отдельно и всегда создаётся первым.

```yaml
kind: VMDisk
metadata:
  name: convert-tools
spec:
  source:
    image:
      name: ubuntu-20.04
  storage: 25Gi
  storageClass: replicated
```

`source.image` — откуда взять содержимое диска. Здесь это готовый образ Ubuntu из
каталога платформы, то есть аналог шаблона VM.

`storage: 25Gi` — размер. Не меньше 25 гигабайт: внутри будет лежать и скачанный
исходный образ, и результат переупаковки. Если сделать меньше, копирование оборвётся на
середине, а диск потом зависнет в состоянии удаления и будет мешаться.

`storageClass: replicated` — где хранить. `replicated` означает три копии на разных
узлах. Аналог — политика хранилища в vSphere.

⚠️ **Версия Ubuntu указана намеренно.** На 24.04 машина не загружается, на 22.04
переупаковка спотыкается о старую базу пакетов внутри CentOS 7. Проверено, чтобы вам не
пришлось.

```yaml
kind: VMInstance
metadata:
  name: convert
spec:
  instanceType: u1.large
  instanceProfile: ubuntu
  runStrategy: Always
  disks:
    - name: convert-tools
```

`instanceType: u1.large` — размер машины, как «шаблон ресурсов» в vSphere: два
процессора и восемь гигабайт. Переупаковка требует памяти.

`instanceProfile: ubuntu` — набор настроек виртуального железа под эту гостевую систему:
какие контроллеры дисков, какая сетевая карта. Ближайший аналог — «Guest OS Type» при
создании VM.

`runStrategy: Always` — держать машину включённой; если упадёт, поднять.

`disks` — какие диски подключить. Ссылка по имени на объект, описанный выше.

```yaml
  cloudInit: |
    #cloud-config
    password: ubuntu
    packages: [ libguestfs-tools, virt-v2v, qemu-utils ]
    runcmd:
      - [ bash, -c, "wget ... mc && chmod +x /usr/local/bin/mc" ]
```

`cloudInit` — инструкции, которые машина выполнит при первом запуске: задать пароль,
поставить пакеты, скачать нужную утилиту. В vSphere это «Customization Specification»,
только описанная текстом.

Здесь ставятся `virt-v2v` для переупаковки и `mc` — консольный клиент для работы с
объектным хранилищем.

⚠️ **Пароль в открытом виде** — только для учебного стенда. На рабочей машине вместо
`password` кладут ssh-ключи.

</details>

**Что делаем внутри машины.** Дожидаемся состояния `Running`, заходим в консоль
(`virtctl console vmi/vm-instance-convert`, логин `ubuntu`, пароль `ubuntu`), вписываем
ключи бакета в `convert.sh` и запускаем.

<details>
<summary><b>Что делает convert.sh, по шагам</b></summary>

Скрипт состоит из пяти шагов, и каждый печатает, чем занят.

**Шаг 1 — проверка аппаратного ускорения.** Смотрит, есть ли `/dev/kvm`. Если процессор
пробрасывается внутрь машины, переупаковка идёт быстро. Если нет — включается
программный режим: медленнее, но работает. Строка `LIBGUESTFS_BACKEND=direct` — это как
раз переключение в такой режим.

**Шаг 2 — скачивание исходного образа.** Берёт `OVA` из общего хранилища воркшопа. В
своём проекте здесь была бы выгрузка из vSphere.

**Шаг 3 — сама переупаковка.**

```bash
virt-v2v -i ova /root/source.ova -o local -os /root/out -of qcow2 -on app
```

`-i ova` — что на входе. `-o local -os /root/out` — куда положить результат.
`-of qcow2` — **обязательный** флаг: без него `virt-v2v` выберет формат по умолчанию, и
платформа такой диск не примет.

Кроме смены формата `virt-v2v` делает вторую, менее заметную работу: подкладывает внутрь
образа драйверы для нового виртуального железа. Система, выросшая в VMware, ожидает
увидеть карты `vmxnet3` и контроллеры `pvscsi`. На новом месте железо другое — `virtio`.
Без этих драйверов машина стартует и не найдёт ни диска, ни сети.

**Шаг 4 — выгрузка в ваш бакет.** `mc alias set` запоминает адрес и ключи, `mc cp`
копирует файл.

**Шаг 5 — ссылка для платформы.**

```bash
mc share download --expire 168h "mybucket/$BUCKET/app.qcow2"
```

Создаёт временную подписанную ссылку на семь дней. Подписанную — значит, по ней файл
скачает кто угодно, но только по этой ссылке и только пока она жива. Открывать бакет
всему миру не нужно.

Ссылку ищите в выводе после слова `Share:` — она понадобится на следующей фазе.

</details>

### Фаза 3. Поднимаем машину на новом месте

📍 **Где:** на ноутбуке.

Вставляете ссылку из предыдущего шага в `03-app-vm.yaml`, в поле `url`, и применяете:

```bash
kubectl apply -f manifests/03-app-vm.yaml
```

<details>
<summary><b>Что внутри 03-app-vm.yaml</b></summary>

Снова два объекта — диск и машина.

```yaml
kind: VMDisk
spec:
  source:
    http:
      url: "ВСТАВЬТЕ_PRESIGNED_URL"
  storage: 10Gi
```

`source.http` вместо `source.image` — вот и вся разница с предыдущей фазой. Там диск
клонировался из каталожного образа, здесь скачивается по ссылке. Платформа сама заберёт
файл, распакует и подготовит диск.

```yaml
kind: VMInstance
spec:
  instanceType: u1.medium
  instanceProfile: centos.7
  disks:
    - name: app-1
```

`instanceProfile: centos.7` — профиль под старую систему. Он важнее, чем кажется: у
CentOS 7 ядро 2016 года, и часть современных настроек виртуального железа оно не
понимает.

</details>

**Заходим внутрь:** логин `root`, пароль `cozydemo`.

⚠️ **Сети внутри не будет.** Это не поломка стенда и не ошибка переупаковки — так и
должно быть. Почему, разберём на пятой фазе, там же и починим.

### Фаза 4. Заказываем базу и очередь

📍 **Где:** на ноутбуке.

```bash
kubectl apply -f manifests/04-managed.yaml
```

**Зачем.** Это и есть главное, ради чего всё затевалось. Перевезти три виртуалки со
своими базами внутри вы могли бы и без нас — но тогда у вас остался бы тот же самый
PostgreSQL, который кто-то поставил в 2019-м, который никто не обновляет и который никто
не бэкапит, потому что «там же скрипт был».

Здесь база и очередь приезжают как позиции каталога: с репликацией, автоматическими
бэкапами и мониторингом, за которые отвечает платформа.

<details>
<summary><b>Что внутри 04-managed.yaml</b></summary>

```yaml
kind: Postgres
metadata:
  name: db
spec:
  replicas: 1
  size: 10Gi
  storageClass: local
  resourcesPreset: t1.micro
  users:
    orders:
      password: Orders2019!
  databases:
    orders:
      roles:
        admin: [ orders ]
```

`users` и `databases` — платформа сама заведёт пользователя `orders`, базу `orders` и
выдаст пользователю права администратора этой базы. Вручную ничего создавать не нужно:
именно поэтому в файле схемы, который мы накатим позже, нет команд `CREATE DATABASE` и
`CREATE USER`.

`replicas: 1` — одна копия, учебный стенд. В рабочей системе ставят больше.

`resourcesPreset: t1.micro` — размер, как «шаблон ресурсов». Самый маленький.

⚠️ **Пароль лежит открытым текстом** прямо в файле, который вы кладёте в репозиторий.
Для учебного стенда так можно, для рабочего — нет: там пароль хранят в хранилище
секретов, а в описании оставляют только ссылку на него.

Ниже в том же файле — объект `kind: Kafka` с очередью и темой `orders`.

</details>

### Фаза 5. Подключаем приложение

📍 **Где:** внутри вашей виртуальной машины.

Три действия строго по порядку. Порядок важен, и вот почему.

**5.1. Чиним сеть** — скрипт `netfix-dhcp.sh`.

<details>
<summary><b>Почему сеть сломана и что делает скрипт</b></summary>

Внутри образа лежит файл `/etc/sysconfig/network-scripts/ifcfg-eth0` — настройки сетевой
карты, которые задали когда-то в VMware. Там прописан статический адрес вида
`192.168.10.x`, шлюз и маска той сети, которой здесь нет и никогда не было.

Машина честно поднимает карту с этим адресом, не получает ответа ни от кого и остаётся
без связи. Ни интернета, ни доступа к базе, ни даже возможности узнать её адрес по
имени.

Скрипт переписывает всего одну строку — `BOOTPROTO=static` на `BOOTPROTO=dhcp` — и
удаляет всё, что относится к старому адресу:

```bash
sed -i 's/^BOOTPROTO=.*/BOOTPROTO=dhcp/; /^IPADDR/d; /^GATEWAY/d; /^NETMASK/d; ...' "$IFCFG"
```

После этого машину нужно **перезапустить**: сетевые настройки CentOS 7 применяет при
загрузке. После перезапуска карта получит адрес от платформы и окажется в той же сети,
что и остальные сервисы.

⚠️ Это правка для **CentOS 7**. В Ubuntu сеть настраивается совсем иначе, файл там
другой. Если будете повторять для своих машин — смотрите, какая система внутри.

**Это и есть самая частая работа при любой миграции.** Перевезти диск — простая часть, на
неё обычно и смотрят. Ломается всегда то, что снаружи: адреса, имена, доступы,
сертификаты. Поэтому в реальном проекте на перевоз машины закладывают день, а на
«доведение до работоспособности» — недели.

</details>

**5.2. Переключаем приложение на новые адреса** — скрипт `connect-managed.sh`.

<details>
<summary><b>Что он меняет</b></summary>

В настройках приложения — файл `/etc/orders/application.properties` — адреса прописаны
**цифрами**:

```properties
spring.datasource.url=jdbc:postgresql://192.168.10.30:5432/orders
spring.kafka.bootstrap-servers=192.168.10.40:9092
```

Это адреса двух других машин, которые остались в прошлом. Скрипт заменяет их на имена
сервисов, которые вы заказали на четвёртой фазе, и перезапускает приложение.

Обратите внимание: подставляются **имена**, а не адреса. Имя не меняется, даже когда
платформа переносит базу на другой узел или переключает копии между собой. Адрес —
меняется. Именно поэтому в рабочих системах прописывают имена, а «прибитые» цифры в
конфиге — то, из-за чего миграции и бывают болезненными.

</details>

**5.3. Создаём таблицы** — файл `orders-schema.sql`.

<details>
<summary><b>Зачем это отдельный шаг</b></summary>

Заказав базу в каталоге, вы получили **пустой сервер**: он работает, в нём заведены база
и пользователь — и всё. Таблиц внутри нет. На старой машине они были, потому что
приложение создало их когда-то при первом запуске, и за годы про это все забыли.

Мы везём приложение, а не его данные, поэтому таблицы нужно создать заново. Файл
`orders-schema.sql` — это список команд, описывающих одну таблицу заказов: номер,
что заказали, состояние, кто создал, кто обработал и когда.

Почему это не объединено с предыдущим шагом: проверка здоровья приложения смотрит только
на то, удалось ли подключиться к базе. Она честно ответит «всё хорошо» и без таблиц —
а вот создать заказ не выйдет.

</details>

## Шпаргалка

> Во всех командах `virtctl` цель указывайте с префиксом `vmi/`
> (`vmi/vm-instance-app-1`), а не голым именем. Под tenant-доступом права выданы на
> subresource `virtualmachineinstances` (vmi), а не на `virtualmachines` (vm) —
> голое имя бьёт в vm-объект и вернёт `forbidden`. Для `port-forward` это ещё и
> синтаксис: без `vmi/` virtctl отвечает `target must contain type and name
> separated by '/'`.

```bash
# зайти в app-VM (root/cozydemo)
virtctl console --namespace=tenant-workshopXX vmi/vm-instance-app-1

# зайти в conversion-VM (login ubuntu / пароль ubuntu)
virtctl console --namespace=tenant-workshopXX vmi/vm-instance-convert
```

Выйти из консоли — `Ctrl+]`. Если после подключения экран пустой, нажмите Enter.
То же самое доступно мышкой: кнопка **VNC** на странице машины в дашборде.

## Финальная проверка: три шага строго по порядку

Здесь спотыкаются чаще всего, поэтому подробно и с указанием, где что выполнять.

### Шаг 1. Погасить firewalld

**Где:** внутри app-VM.

Мигрированный CentOS принёс правила из прошлой жизни и наружу открывает только SSH.
Порт приложения 8080 закрыт, поэтому и `port-forward`, и проверки будут выглядеть
так, будто приложение не работает. Гасим до всех остальных проверок:

```bash
systemctl stop firewalld
systemctl disable firewalld
```

Убедиться, что приложение живо изнутри самой машины:

```bash
curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/actuator/health
```

`200` — база и очередь на месте. `503` — возвращайтесь к сети: `netfix-dhcp.sh`
и перезагрузка, managed-сервисы ещё не резолвятся.

### Шаг 2. Схема базы

**Где:** внутри app-VM. Она уже в сети кластера и видит базу по имени —
ставить клиент на ноутбук не нужно.

**Клиент psql.** Штатный клиент CentOS 7 — версии 9.2, он не умеет аутентификацию
SCRAM и отвечает `psql: SCRAM authentication requires libpq version 10 or above`.
Нужен клиент 10 или новее; для CentOS 7 в репозитории PGDG доступен максимум 15-й:

```bash
yum install -y https://download.postgresql.org/pub/repos/yum/reporpms/EL-7-x86_64/pgdg-redhat-repo-latest.noarch.rpm
```

Новый клиент кладётся мимо `PATH` — это вторая ловушка, та самая «psql: command not found»:

```bash
yum install -y postgresql15
command -v psql || ls /usr/bin/psql /usr/pgsql-*/bin/psql 2>/dev/null
```

Если нашёлся в `/usr/pgsql-*/bin/`, добавьте каталог в `PATH` на текущую сессию
(версию подставьте из вывода выше) и проверьте:

```bash
export PATH="$PATH:/usr/pgsql-15/bin"
psql --version
```

**Куда подключаться.** Короткое имя изнутри гостя не резолвится, нужен полный адрес
сервиса — со своим номером вместо `XX`:

```
postgres-db-rw.tenant-workshopXX.svc.cozy.local
```

**Пароль.** Роль `orders`, пароль `Orders2019!` — он прописан в
`manifests/04-managed.yaml`, искать его нигде не надо.

**Накатываем схему.** Файл `scripts/orders-schema.sql` из этого репозитория:

```bash
PGPASSWORD='Orders2019!' psql \
  -h postgres-db-rw.tenant-workshopXX.svc.cozy.local -U orders -d orders \
  -f orders-schema.sql
```

Проверить, что таблица на месте:

```bash
PGPASSWORD='Orders2019!' psql \
  -h postgres-db-rw.tenant-workshopXX.svc.cozy.local -U orders -d orders -c '\dt'
```

Отдельный грант под суперпользователем не нужен: роль `orders` входит в `orders_admin`,
который владеет и базой, и схемой `public`, — права на создание таблиц у неё уже есть.

Почему это отдельный шаг: проверка здоровья смотрит только на подключение к базе
и честно ответит `200` даже без таблицы. А вот создать заказ не выйдет — придёт `500`.

### Шаг 3. Проброс порта и проверка снаружи

**Где:** на ноутбуке.

```bash
virtctl port-forward --namespace=tenant-workshopXX vmi/vm-instance-app-1 8080:8080
```

Окно не закрывайте: туннель живёт, пока команда работает. Во втором окне:

```bash
# health, 200 значит Postgres и Kafka на месте
curl -s http://localhost:8080/actuator/health

# создать заказ: запись уходит в Postgres, событие — в Kafka
curl -s -X POST http://localhost:8080/api/orders \
  -H 'Content-Type: application/json' -d '{"item":"test"}'

# посмотреть список
curl -s http://localhost:8080/api/orders
```

Заказ создался — путь пройден целиком.

## На чём ещё легко застрять

Для conversion-VM берите только `ubuntu-20.04`. На 24.04 ядро паникует, на 22.04
virt-v2v не разбирает старую RPM-базу CentOS 7.

VMDisk под каталожный образ должен быть больше самого образа, иначе клон не
пройдёт, а диск потом зависает в Terminating. Для ubuntu-20.04 хватает 25Gi.

На свежей app-VM сначала netfix, потом connect, именно в таком порядке. Иначе
приложение не увидит managed.

Конвертер после третьей фазы не нужен и держит 8Gi из квоты тенанта. Удаляйте оба
объекта — машину и диск:

```bash
kubectl delete vminstance convert --namespace tenant-workshopXX
kubectl delete vmdisk convert-tools --namespace tenant-workshopXX
```
